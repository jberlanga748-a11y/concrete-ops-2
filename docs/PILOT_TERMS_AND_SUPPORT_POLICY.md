# Apex HQ Pilot Terms And Support Policy

Status: draft for founder-led pilots, not legal advice
Owner: Apex HQ founder
Use with: `docs/FOUNDER_PILOT_ONBOARDING_PACKET.md`, `docs/FIRST_10_CUSTOMERS_PLAN.md`, and `docs\CUSTOMER_DATA_POLICY_DRAFT.md`

## Purpose

This draft sets the operating rules for early Apex HQ pilots so the founder can start controlled contractor pilots without overpromising product scope, support, billing, automation, or legal readiness.

A lawyer should review formal terms before wider paid launch, public self-serve signup, automated billing, larger customers, or any regulated data/security commitments.

## Current Pilot Position

Apex HQ is available for founder-led demos and controlled pilots.

Use this language:

```text
Apex HQ is opening controlled founder-led pilots for contractors who want to test one real workflow around estimates, job handoff, field proof, owner review, and follow-up.
```

Do not present the pilot as:

- broad public self-serve SaaS
- enterprise procurement-ready software
- a payroll, accounting, or QuickBooks replacement
- a guaranteed lead or revenue service
- an AI autopilot that sends, prices, approves, schedules, or orders automatically

## Pilot Scope

Each pilot should focus on one workflow:

```text
estimate/job setup -> field handoff -> photo/report proof -> owner review -> follow-up
```

Allowed during pilot:

- guided setup for one contractor workspace
- owner/admin setup help
- one field user or small crew workflow test
- existing leads, estimates, jobs, reports, uploads, tickets, checklists, and support handoff
- day-3 check-in
- day-10 value review
- founder-led troubleshooting

Not included during pilot:

- guaranteed leads, jobs, revenue, or payment speed
- custom feature commitments
- automated email/SMS outreach
- hidden GPS tracking
- payroll, accounting, or tax workflows
- enterprise SSO/MFA/SCIM/SLA commitments
- Stripe, checkout, invoices, or payment collection unless separately approved later
- customer portal login or self-serve customer approvals unless separately built and approved later

## Pilot Length

Default pilot length: 14 days.

Recommended structure:

| Day | Step | Purpose |
| --- | --- | --- |
| 0 | Kickoff | Pick one workflow, users, and success criteria. |
| 1-2 | Setup and first use | Confirm owner/admin and field user can complete the first action. |
| 3 | Check-in | Remove friction and identify blockers. |
| 4-9 | Real workflow use | Use Apex HQ on real estimates, jobs, proof, or follow-ups. |
| 10 | Value review | Decide whether the workflow is worth continuing. |
| 14 | Continue/adjust/stop | Choose next workflow, founder pricing, or stop cleanly. |

## Customer Responsibilities

The contractor should provide:

- one owner/admin contact
- one field lead if field workflow is included
- one real workflow to test
- accurate setup information
- prompt feedback on blockers
- day-3 and day-10 availability
- permission before any testimonial, quote, logo, screenshot, or real customer example is used publicly

## Apex HQ Responsibilities

Apex HQ should provide:

- guided setup for the selected workflow
- clear expectations about what is and is not included
- support through agreed channels
- reasonable response to pilot blockers
- conservative claims about current product readiness
- role-safe handling of owner/admin and field user access
- no public use of customer names, data, screenshots, or quotes without permission

## Support Policy

Support is founder-led during pilots.

Support intake should capture:

- company name
- user role
- workflow/page
- issue summary
- blocker level
- screenshot or short screen recording when practical
- workaround
- promised follow-up time
- whether the issue affects the selected pilot workflow

Suggested support priority:

| Priority | Definition | Target response |
| --- | --- | --- |
| P0 | Cannot access the app, data exposure concern, or role/security issue. | Same day, pause pilot workflow if needed. |
| P1 | Selected pilot workflow is blocked. | Same business day when practical. |
| P2 | Workaround exists or issue affects a non-pilot workflow. | Next check-in or next practical work block. |
| P3 | Copy, polish, training, or future idea. | Log for later; do not promise a build. |

## Support Boundaries

Do not promise:

- custom feature builds during the pilot
- data imports beyond what the founder approves manually
- accounting/payroll reconciliation
- automatic outbound messaging
- guaranteed uptime or enterprise SLA
- same-day fixes for non-critical issues

Safe wording:

```text
I will log that. For this pilot, I want to keep the test focused on the workflow we picked so we can tell whether Apex HQ is actually useful before expanding scope.
```

## Pricing And Payment Position

For current pilots:

- pricing is discussed after fit and workflow value are clear
- founder pricing can be offered manually
- no Stripe, checkout, invoice automation, or self-serve plan changes are part of this policy
- no long-term contract should be implied during the 14-day pilot unless explicitly agreed later

Safe pricing wording:

```text
If the pilot proves useful, we can match you to Basic, Premium, or Elite founder pricing based on what you actually used. I would rather fit the package to the workflow than oversell you.
```

## Data And Privacy Expectations

Use `docs/CUSTOMER_DATA_POLICY_DRAFT.md` for the customer-facing data handling summary.

Minimum pilot expectations:

- do not show one company's workspace to another company
- do not show field users pricing, margins, payroll, admin settings, billing, or unrelated jobs
- do not use real customer data in demos without permission
- do not publish screenshots, testimonials, logos, or quotes without permission
- do not ask for sensitive data that is not needed for the selected pilot workflow

## Testimonial And Proof Permission

Only ask for proof after real value.

Safe ask:

```text
Can I use one sentence from you about what Apex HQ helped clean up? No hype, just what changed. I can keep it anonymous if you prefer.
```

Before using proof publicly, capture:

- exact quote or asset
- name/company permission
- anonymous option if requested
- where it can be used
- date permission was given

## Pilot End States

Continue:

- choose package direction
- confirm founder pricing
- pick next workflow
- schedule onboarding/check-in

Adjust:

- narrow the workflow
- add training
- fix setup confusion
- retest before charging

Stop:

- document why
- export or preserve any agreed customer records
- ask for feedback
- do not pressure for testimonial or referral

## Internal Checklist Before Starting A Pilot

- Pilot contact is a good-fit contractor.
- One workflow is selected.
- Success criteria are written in plain language.
- Owner/admin user is identified.
- Field user is identified if needed.
- Day-3 and day-10 check-ins are scheduled.
- Customer data expectations are shared.
- No unsupported claims were made.
- No automatic billing/payment promise was made.
- No custom feature promise was made.

## Open Legal/Operations Items

Before wider paid launch, prepare or review:

- formal terms of service
- privacy policy
- acceptable use policy
- payment and cancellation terms
- data retention/export process
- support SLA or support limits
- testimonial release language
- incident/contact process for security or data concerns
