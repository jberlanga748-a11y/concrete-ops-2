# Apex HQ Agent Estimate Send Execution Gate Plan

Status: Phase 1 safety plan only. Do not implement autonomous email, text, bid submission, customer contact, sent-status changes, contact history, invoice creation, job conversion, or production deploys from this document without a separate explicit approval.

## Objective

Define the safety boundary for a future owner/admin-controlled gate that could let Apex Assistant help prepare an estimate/proposal send action without bypassing human approval.

The current shipped state is intentionally safer:

- Apex Assistant can generate proposal review packets.
- Apex Assistant can record redacted audit events.
- Apex Assistant can create internal draft estimates from leads only after a human click.
- Apex Assistant can prepare an audit-only estimate send review packet.
- Apex Assistant cannot send email, submit bids, contact customers, mark estimates sent, create invoices, collect payments, convert estimates to jobs, or update field records.

## Repository Findings

- Existing manual send endpoint: `POST /api/estimates/:id/send` in `server/index.js`.
- Existing send behavior:
  - Requires authenticated estimate management permission.
  - Requires configured email provider.
  - Requires customer email.
  - Builds proposal email subject and body.
  - Builds PDF attachment.
  - Calls `sendEstimateEmail(...)`.
  - Marks the estimate `sent`.
  - Sets `sentAt`, `sentBy`, `sentTo`, `emailSubject`, and `providerMessageId`.
  - Writes activity and audit events.
- Existing assistant send-review endpoint: `POST /api/agent-action-proposals/prepare-estimate-send`.
- Existing assistant send-review behavior:
  - Requires AI Office audit access and estimate management permission.
  - Requires `estimate-packet-review`.
  - Requires customer email.
  - Writes generated/send-ready audit events.
  - Returns review metadata.
  - Does not call `sendEstimateEmail(...)`.
  - Does not mark the estimate sent.
  - Does not write contact history, create jobs, create invoices, submit bids, or contact customers.

## Non-Negotiable Safety Rules

- No assistant action may send a proposal unless the current user explicitly clicks a send execution control in the Estimates workflow.
- Field users must remain blocked from pricing, proposal, send, AI Office, and internal takeoff controls.
- Server-side permissions must be the authority. UI hiding is not authorization.
- Package gates must not be weakened.
- Tenant/company scoping must be enforced through existing server lookup helpers.
- The agent may not submit bids, upload to portals, use browser automation for customer portals, bypass CAPTCHA/MFA/paywalls, or send customer messages outside approved app flows.
- The agent may not store credentials, tokens, cookies, MFA codes, or private portal instructions.
- Production remains locked unless there is a backup-first release approval.

## Proposed Future Architecture

### Phase 2D: Human Send Execution Gate

Add a narrowly scoped endpoint only if explicitly approved later:

`POST /api/agent-action-proposals/execute-estimate-send`

Minimum requirements:

- Auth required.
- Owner/admin/estimator role must already pass the same estimate-send domain gate as manual send.
- AI Office and estimate packet entitlements must pass.
- Target estimate must be company-scoped and visible to the current user.
- Estimate must not be archived.
- Estimate must not already be sent.
- Estimate must have customer email.
- Email sending must be configured.
- A prior `agent.proposal.generated` event must exist.
- A prior `agent.proposal.send_ready_for_human` event must exist.
- Request must include an explicit human confirmation phrase or UI-generated confirmation token.
- Request must include a fresh review timestamp generated by the server or a short-lived server-issued review nonce.
- Server must re-read the estimate and rebuild subject/body/PDF at execution time.
- Server must call the same send implementation used by `POST /api/estimates/:id/send`.
- Server must write a distinct audit event such as `agent.proposal.send_executed_by_human`.

### Recommended Safer First Implementation

Before any new execution endpoint, refactor the existing manual send endpoint into a shared server helper:

- `prepareEstimateSendContext(...)`
- `executeEstimateEmailSend(...)`
- `markEstimateEmailSent(...)`

Then both manual send and future agent-approved human send can use the same permission checks and mutation path. This avoids duplicated send behavior and makes tests stronger.

## UI Flow

1. Assistant shows an estimate packet review.
2. User clicks `Prepare send review`.
3. Assistant writes audit-only send-ready event.
4. UI shows: "No email has been sent. Use the normal send controls after final review."
5. Future approved version could show a separate `Send from reviewed packet` button only inside the Estimates workflow, not in a floating assistant chat.
6. Button must require an explicit confirmation modal with:
   - recipient
   - estimate title
   - total
   - attachment/PDF summary
   - reply-to/company identity
   - disclaimer that this contacts the customer
7. On submit, server must revalidate and execute. Client-provided recipient, total, subject, or PDF data cannot be trusted as authority.

## Required Negative Tests

Server tests:

- Employee/foreman receives 403.
- Package-locked user receives 403.
- User without estimate manage permission receives 403.
- Missing prior generated event receives 409.
- Missing send-ready event receives 409.
- Missing confirmation receives 400.
- Archived estimate receives 400.
- Already sent estimate receives 409.
- Missing customer email receives 400.
- Unconfigured email provider receives 503.
- Unsupported proposal type receives 403.
- Cross-company estimate ID cannot be sent.
- Unsafe payload text containing credential/token/bid-submission instructions is rejected or redacted before audit.
- Successful send calls email exactly once, marks sent once, and writes manual plus agent-specific audit trail.

Frontend tests:

- Field users never see send execution controls.
- Premium/Elite package states match entitlements.
- Send-review prepared state does not imply sent.
- Confirmation modal uses customer-contact language.
- Button is disabled until review packet is ready.

Hosted demo checks:

- Backup-first Fly demo deploy only.
- `/api/ready`.
- Hosted route smoke.
- Admin auth smoke when demo password is available.
- Employee restricted route smoke.
- Send execution test only with a safe test recipient/domain and explicit approval.

## Risks

| Risk | Level | Mitigation |
| --- | --- | --- |
| Customer contact | High | Keep no-outbound default; require explicit human execution and confirmation |
| Bid submission confusion | High | Copy must say email proposal only, never portal bid submission |
| Permission bypass | High | Reuse existing estimate send permission path and server-side scoping |
| Duplicate emails | High | Idempotency guard by estimate state and short-lived confirmation nonce |
| Wrong recipient/price | High | Server re-reads estimate, customer, settings, totals, and PDF at execution time |
| Email provider failures | Medium | Surface provider errors, do not mark sent unless provider succeeds |
| Audit gaps | Medium | Append generated, ready, and executed events with redacted metadata |

## GO / NO-GO

GO now:

- Planning.
- Tests around current no-outbound send review.
- Refactoring manual send internals if behavior remains identical and verified.

NO-GO without explicit approval:

- Any endpoint that calls `sendEstimateEmail(...)` from an agent route.
- Any assistant UI that says or implies autonomous send.
- Any production deploy.
- Any customer email, text, call, or bid submission.
- Any use of browser automation to submit customer or GC portal forms.

## Recommended Next Safe Task

Do not implement send execution next unless the owner explicitly approves the customer-contact boundary. The safer next autonomous build task is to continue component extraction or agent context read models that do not mutate customer-facing workflow state.
