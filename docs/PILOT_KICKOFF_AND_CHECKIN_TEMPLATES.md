# Apex HQ Pilot Kickoff And Check-In Templates

Status: active pilot operator template
Use with: `docs/FOUNDER_LED_DEMO_EXECUTION_RUNBOOK.md`, `docs/DEMO_RECAP_AND_PILOT_FIT_TEMPLATES.md`, and `docs/FOUNDER_PILOT_ONBOARDING_PACKET.md`

## Purpose

Use this after a strong-fit demo turns into a controlled founder-led pilot.

The goal is to keep the first 14 days narrow, useful, and honest. Apex HQ should prove one workflow before John expands setup, adds users, or discusses a larger package.

Do not use this to promise custom builds, guaranteed leads, accounting/payroll replacement, automatic sending, automatic pricing, or full-company migration.

## Kickoff Agenda

Timebox: 30 to 45 minutes.

| Step | Action | Outcome |
| --- | --- | --- |
| 1 | Confirm the one workflow. | Everyone agrees what is being tested. |
| 2 | Confirm users and roles. | Owner/admin and field roles stay clean. |
| 3 | Set up or review the first real record. | Pilot starts from real work, not fake examples. |
| 4 | Show the field action. | Field user knows the one thing to do first. |
| 5 | Define proof. | Everyone knows what photo/report/update counts as success. |
| 6 | Confirm check-ins. | Day-3 and day-10 dates are on the calendar. |
| 7 | Restate boundaries. | No custom build, no autopilot, no accounting/payroll, no guaranteed leads. |

Kickoff close:

```text
For the first 14 days, I would judge Apex HQ on this one workflow only: [workflow]. If it reduces chasing or keeps proof easier to find, we can talk about the right package. If it does not, we adjust or stop.
```

## Success Criteria Examples

Pick two or three. Keep them measurable and practical.

- Owner/admin logs in and can find the pilot workflow without help.
- One real estimate or job is entered or reviewed.
- One field user logs in and completes the agreed field action.
- One photo, report, ticket, checklist, or job update is submitted.
- Owner can review proof without searching through texts.
- Follow-up date or next action is visible.
- Contractor can name what Apex HQ cleaned up.
- Contractor would pay to keep the workflow if the pilot continues working.

Avoid success criteria like:

- "Company fully migrated."
- "Crew adoption solved."
- "More leads guaranteed."
- "Accounting/payroll replaced."
- "AI handles it automatically."

## First Workflow Setup Checklist

Use only the checklist that matches the pilot workflow.

### Lead Or Estimate Workflow

- Confirm customer or prospect name.
- Confirm job type and location.
- Add rough scope notes.
- Add estimate notes, options, or packet context if available.
- Add follow-up date.
- Confirm who owns the next follow-up.
- Confirm what would make this ready to convert to a job.

### Job Handoff Workflow

- Confirm job name and address.
- Confirm owner/admin reviewer.
- Confirm foreman or field lead.
- Add scope notes and handoff expectations.
- Confirm schedule/today work expectations if relevant.
- Confirm what field proof is required.
- Confirm where owner reviews proof.

### Photo, Report, Or Proof Workflow

- Confirm the first job to test.
- Confirm required photo/report/proof.
- Confirm who submits it.
- Confirm deadline or work moment.
- Confirm owner/admin review path.
- Confirm what still happens by text today.

## Day-1 And Day-2 Field Action Checks

Use this as a quick internal check, not a customer-facing survey.

```text
Company:
Pilot workflow:

Day 1:
- Owner/admin logged in? yes/no
- First record reviewed? yes/no
- Any login/setup issue?
- Support follow-up needed?

Day 2:
- Field user logged in? yes/no/not needed
- Field action attempted? yes/no/not needed
- Photo/report/update submitted? yes/no/not needed
- What still went through text?
- Blocker? yes/no
```

If a field user cannot complete the agreed action by day 2, treat that as a pilot risk and check in before day 3 if possible.

## Day-3 Check-In

Goal: remove friction early and decide whether the workflow is still worth testing.

Questions:

- Did the owner/admin log in?
- Did the field user understand what to do?
- Did one photo, report, job update, or follow-up action happen?
- What still went through text?
- Where did the workflow feel slower than the old way?
- What confused the owner?
- What confused the field user?
- Is this still the right workflow to test?
- What is the next real job, estimate, or field action?

Internal decision:

| Result | Action |
| --- | --- |
| Working | Keep pilot narrow and continue to day 10. |
| Confusing but fixable | Reset training, simplify the workflow, and continue. |
| Product blocker | Log exact blocker before any build decision. |
| Poor fit | Stop or move back to discovery. |

Day-3 follow-up:

```text
Thanks for the day-3 check-in. For the rest of the pilot, I would keep Apex HQ focused on [workflow].

The next useful action is [next action].

I have [support item] on my side. No new custom build promise here; I want to see whether the current workflow is useful enough on real work first.
```

## Day-10 Value Review

Goal: decide continue, adjust, or stop before the end of the 14-day pilot.

Score each item 0 to 2.

| Signal | 0 | 1 | 2 |
| --- | --- | --- | --- |
| Workflow was used on real work | no | partly | yes |
| Owner/admin saw value | no | maybe | yes |
| Field action happened if needed | no | partly | yes |
| Chasing was reduced | no | unclear | yes |
| Proof was easier to find | no | somewhat | yes |
| Follow-up was clearer | no | somewhat | yes |
| Support load is manageable | no | maybe | yes |
| Contractor would pay to continue | no | maybe | yes |

Decision guide:

- 13-16: continue and discuss Basic/Premium/Elite direction.
- 9-12: adjust workflow, extend briefly only if the next test is clear.
- 5-8: stop selling, capture feedback, and revisit later.
- 0-4: not a fit now.

Review questions:

- What did Apex HQ help organize?
- What still felt clunky?
- Did it reduce owner chasing?
- Did it make proof or reports easier to find?
- Did the field user understand the one action?
- Which package direction seems honest: Basic, Premium, or Elite?
- Would they pay to keep using this workflow?
- What should not be built yet?

## Continue, Adjust, Or Stop

### Continue

Use when the workflow created real value.

Next steps:

- confirm package direction
- confirm next workflow
- confirm users to keep
- confirm support expectations
- ask for permission before using any quote, screenshot, or company reference

Close:

```text
It sounds like Apex HQ is useful enough around [workflow] to keep going. I would keep the next step practical: choose the right package, keep the workflow narrow, and add the next workflow only after this one stays clean.
```

### Adjust

Use when there is interest but the first workflow was too broad or confusing.

Next steps:

- narrow to one record or one field action
- remove extra users
- reset owner/admin training
- reset field action expectations
- schedule one short retest

Close:

```text
I would not call this a win yet, but I also would not throw it out. The cleanest move is to narrow the workflow to [specific action] and retest that before talking about a broader rollout.
```

### Stop

Use when the product is not a fit today.

Next steps:

- document why
- thank them for the feedback
- do not push pricing
- ask for referral only if the conversation stayed positive and the referred company is a better fit

Close:

```text
Based on this pilot, I would not push Apex HQ on you right now. The main need sounds like [reason], and I do not want to oversell what the product is best at today.
```

Use the same support structure as the customer success playbook.

```text
Company:

Device/browser:
Issue:
Steps:
Expected:
Actual:
Screenshot or recording:
Blocking? yes/no
Severity: P0 / P1 / P2 / P3
Workaround:
Promised follow-up time:
```

Severity:

- P0: security, company data, role leakage, login down.
- P1: pilot-blocking workflow failure.
- P2: important friction with a workaround.
- P3: minor polish, copy, or training issue.

## Referral And Testimonial Timing

Do not ask before value is real.

Ask only after:

- contractor says the workflow helped
- owner/admin can name what changed
- pilot is continuing or ended positively
- permission is explicit

Testimonial ask:

```text
Can I use one sentence from you about what Apex HQ helped clean up? Nothing hype. Just what changed.
```

Referral ask:

```text
Is there one contractor you know who has the same kind of estimate, job handoff, or field proof mess this helped with?
```

Do not publish names, logos, screenshots, quotes, or job details without explicit permission.

## Product Build Trigger

Start a product task only if the pilot exposes a real blocker.

Use:

```text
Company:
Pilot workflow:
Exact pain:
Who experienced it:
Role:
Current workaround:
Why current Apex HQ cannot handle it:
How many pilots/demos have shown this:
Pilot impact:
Smallest safe product change:
Permission/package/role risks:
Verification needed:
```

Build only when the issue is one of:

- role or permission issue
- visible demo or pilot data problem
- broken guided workflow
- mobile field blocker
- repeated onboarding confusion that blocks conversion
- narrow missing workflow required for a good-fit pilot

Do not build because a prospect casually mentioned an idea.

## Safe Claims During Pilot

Safe:

- "We are testing one real workflow."
- "The goal is less scattered information and less owner chasing."
- "AI help is review-first where available."
- "We will decide continue, adjust, or stop based on day-10 value."

Avoid:

- "This guarantees more jobs."
- "This replaces QuickBooks, payroll, or your accountant."
- "AI will handle pricing, approvals, or messages automatically."
- "We can build whatever you need."
- "Your crew will definitely adopt it."
- "This is enterprise-ready."
