# Apex OS Route Permission Map

Last updated: 2026-06-07

Purpose: concise post-Phase-10 map of current Apex OS private Jarvis routes and capabilities. This is an audit/control document only; it does not add routes, schema, auth/session changes, production behavior, or execution capability.

Global boundary:

- Apex OS is John's private operator-only layer inside Apex HQ.
- Server gate: authenticated user plus `canAccessApexOs(user)`, which requires operator access, an office/operator role, and the default Apex HQ workspace.
- Field, customer, demo, estimator, normal admin, pilot, and switched-company users must not see Apex OS routes, nav, private settings, memory, tasks, runs, approvals, or life-operator data.
- Level 2 internal action engine is active for private, local, reversible, low-risk Apex OS state only. Consequential/external actions remain interrupt/confirmation-gated and currently non-executing.
- Level 3 external action preparation now has a response-only packet builder route at `POST /api/apex-os/external-preparation-packets`. It does not persist packets, create approval-submit/execute routes, call connectors, or change external systems. It remains operator-only, preparation-only, and forces `canExecuteNow: false`, `canExecuteAfterApproval: false`, `executionLocked: true`, and `noExecutionTokens: true`.
- Jarvis Device Layer v0 is active as mock-only shared planning helpers. Home Assistant Connector v1 adds operator-only status, preview, and execute routes. Execution remains disabled unless Home Assistant is enabled, execution is enabled, the kill switch is off, the entity/service/payload is allowlisted, a short-lived preview guard is valid, and John provides the exact confirmation phrase.
- Local Network + Remote Access Jarvis Layer is documented only. No router adapter, connected-device discovery endpoint, pause/unpause endpoint, family-device control, VPN/tunnel control, remote home bridge, network scan, credential path, or remote device-control route exists yet.
- Local-First Provider Policy v0 is active as a deterministic server-consulted policy for Ask Apex and Knowledge Intelligence. llama.cpp Provider v1 is now the primary local Ask Apex and Knowledge Intelligence brain through policy-gated local `/completion` with GPT-OSS when the sidecar/model is available. Ollama Provider v0/v1 remains operator-only legacy fallback/status/manual inventory support through localhost `/api/tags`, `/api/ps`, and gated `/api/chat`. Workstation Brain Mode and Apex Local Agent Speed preserve bounded Ollama fallback profiles, direct local operator persona for Apex Personal OS/local operator routes, first-token timing receipts when local streaming is available, and passive benchmark-history summaries; they do not add a new runtime, cloud provider, external execution, or customer-facing AI. No LM Studio adapter, cloud override endpoint, model install, OpenAI removal, Local Research/Search Provider, or contractor AI migration exists yet. Current Apex OS provider routes still contain OpenAI server-side code paths, but `OPENAI_API_KEY` alone is not enough to authorize Apex OS text-provider cloud calls.
- Apex Autonomous Build Loop v0 is active as a private operator-only local coding coordinator. It can start/stop Apex-owned coding mode, create scoped build-loop receipts, and route allowlisted local repair requests through existing Builder/Self-Fix controlled patching and validation. It cannot perform raw file-system autonomy, git reset/checkout/clean/commit/push, deploy, production mutation, schema/auth/session changes, secret access, destructive deletion, customer-visible writes, sends, spending, ordering, booking, arbitrary desktop/browser control, or unrelated process control.
- `canExecuteAfterApproval` remains false for current Apex OS approval records because approval records still do not execute actions.

Post-Phase-10 hardening note:

- Approval packet records may be approved/rejected/deferred, but those records intentionally leave `canExecuteAfterApproval` false. Level 2 internal receipts are now separate from approval packets. Any consequential/external execution phase would need a separate approved design, permission review, route map update, tests, and visual QA before execution exists.
- Level 3 external preparation packets, when implemented, must remain separate from Level 4 execution. A Level 3 packet may include future approval language, preview hash, payload hash, cancellation path, fallback/manual steps, and receipt draft, but it must not mint execution tokens or change any external system.
